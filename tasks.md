# Craft Build Plan — Sapphire Health Tracker v2

## 1. Implementation baseline

Implement **Option A: modular TypeScript monolith with separate API and worker roles**, plus a local vLLM inference sidecar.

### Fixed technology choices

| Area | Choice |
|---|---|
| Runtime | Node.js 22 LTS, TypeScript 5.x |
| API | Fastify, `@fastify/cookie`, `@fastify/multipart`, RFC 9457 errors |
| Database | PostgreSQL 16, Drizzle ORM, pgvector, pgcrypto |
| Jobs | pg-boss |
| Frontend | React 18, Vite, TanStack Query, React Router |
| Styling/charts | Tailwind CSS, Recharts |
| Validation | Zod, JSON Schema |
| Authentication | Argon2id, server-side sessions, TOTP |
| Object storage | MinIO |
| AI runtime | vLLM OpenAI-compatible HTTP endpoint |
| Observability | OpenTelemetry, Prometheus, Grafana, Loki |
| Testing | Vitest, Fastify `inject`, Playwright, Testcontainers |
| Deployment | Docker Compose, Caddy |
| Package management | pnpm workspaces |

### Scope boundary

Included in v2:

- Responsive web/PWA member experience.
- Manual health observations.
- Device integration abstraction and approved device adapters.
- CSV/Apple Health-style import.
- Deterministic summaries, trends, goals, classifications, and alerts.
- Free and premium entitlements.
- Stripe Checkout, Customer Portal, signed webhooks, reconciliation.
- Weekly wellness insights.
- Non-diagnostic AI wellness assistant.
- Human-confirmed structured observation suggestions.
- Audit, consent, access control, privacy, and operational tooling.

Explicitly excluded:

- EHR or clinician exchange.
- Diagnosis, treatment recommendations, dosage instructions, or medication changes.
- Offline writes.
- Native iOS or Android applications.
- Card data storage.
- AI-controlled database writes, billing actions, or notifications.

# 4. Core implementation patterns

## 4.1 Deterministic domain services

Business-critical behavior remains ordinary, reviewable TypeScript.

```ts
export function classifyBloodPressure(input: {
  systolic: number;
  diastolic: number;
  thresholds: BloodPressureThresholds;
}): BloodPressureClassification {
  if (
    input.systolic >= thresholds.crisis.systolic ||
    input.diastolic >= thresholds.crisis.diastolic
  ) {
    return "crisis";
  }

  if (
    input.systolic >= thresholds.stage2.systolic ||
    input.diastolic >= thresholds.stage2.diastolic
  ) {
    return "stage_2";
  }

  if (
    input.systolic >= thresholds.stage1.systolic ||
    input.diastolic >= thresholds.stage1.diastolic
  ) {
    return "stage_1";
  }

  if (
    input.systolic >= thresholds.elevated.systolic ||
    input.diastolic >= thresholds.elevated.diastolic
  ) {
    return "elevated";
  }

  return "normal";
}
```

Thresholds must be:

- Seeded from an approved source.
- Versioned with `source_ref`.
- Reviewed by the designated clinical/product owner.
- Tested with boundary and null cases.
- Never inferred by an AI model.

## 4.2 Canonical unit normalization

Implement:

```text
packages/domain/observations/src/normalize.ts
```

Functions:

```ts
normalizeObservationInput(input): NormalizedObservation
normalizeWeight(value, unit): { value: number; unit: "kg" }
normalizeSleep(value, unit): { value: number; unit: "minutes" }
normalizeBloodPressure(value, unit): ...
resolveMeasuredAt(value, timezone): Date
```

Rules:

- Reject unsupported units.
- Reject NaN, infinity, impossible values, and dates outside configured limits.
- Resolve ambiguous local timestamps using the member timezone.
- Persist canonical units only.
- Preserve original input in audit metadata where policy allows.

Property tests should verify conversion round trips and DST transitions.

## 4.3 Idempotent writes

Every mutating endpoint requires `Idempotency-Key`.

```ts
withIdempotency({
  userId,
  key,
  requestHash,
  execute: async (tx) => {
    // Persist idempotency record and domain mutation atomically.
  },
});
```

A reused key with a different request body returns `409 Conflict`.

Device imports use:

```text
(device_link_id, vendor_measure_id)
```

as the idempotency key.

## 5.2 Prompt versioning

Prompts are committed files:

```text
prompts/assistant-chat/v1.md
prompts/assistant-chat/v1.schema.json
```

Build process:

1. Read prompt and schema files.
2. Calculate SHA-256.
3. Validate schema syntax.
4. Upsert into `ai_prompt_versions` as `candidate`.
5. Store model profile and template hash.
6. Permit production use only after admin promotion.

Prompt promotion requires:

```ts
promotePrompt({
  name,
  version,
  evalRunId,
  actorUserId,
});
```

Validation:

- Admin permission.
- Eval run exists.
- Eval run status is `passed`.
- Prompt version is present and hash matches the repository artifact.
- Audit event is written.

Rollback is performed by promoting a previous passing version.

## 5.3 Structured output validation and retry

Implement:

```text
packages/ai/src/orchestration/structured-generation.ts
```

Flow:

```text
generate
  → parse JSON
  → validate JSON Schema
  → validate with Zod
  → cross-check numeric claims against fact-pack
  → guardrail scan
  → persist interaction
```

Retry policy:

- Initial generation.
- One repair attempt with validation errors.
- Second failure uses deterministic fallback.
- Numeric mismatch is never repaired by asking the model again; it is discarded.
- Persist `repair_attempts`, `schema_valid`, and `fallback_used`.

Example schemas:

```ts
const ObservationSuggestionSchema = z.object({
  kind: z.enum(["heart_rate", "weight_kg", "sleep_minutes", "symptom", "meal"]),
  value: z.number().finite().optional(),
  unit: z.string().optional(),
  note: z.string().max(500).optional(),
  confidence: z.number().min(0).max(1),
});
```

Confidence routing:

```text
confidence >= 0.70
  → show suggestion for explicit member confirmation

confidence < 0.70
  → do not show a writeable suggestion
  → offer a clarification prompt or ordinary free-text note path

never auto-write an AI suggestion
```

## 5.4 AI call telemetry

Each call must record:

- Feature.
- Prompt name and version.
- Prompt SHA-256.
- Model ID and digest.
- Runtime.
- Input and output token counts.
- Time to first token.
- Total latency.
- Queue wait time.
- Retry count.
- Schema validity.
- Guardrail verdict.
- Rules hit.
- Fallback status.
- Fact-pack hash.
- Retrieval IDs.
- User feedback, where available.

Do not log raw prompts, raw health records, or assistant text by default.

Use structured logs:

```ts
logger.info({
  event: "ai.call.completed",
  interactionId,
  feature,
  modelId,
  modelDigest,
  promptVersion,
  latencyMs,
  ttftMs,
  inputTokens,
  outputTokens,
  fallbackUsed,
  guardrailVerdict,
});
```

Prompt and response retention must be configurable and disabled by default in production.

## 5.5 AI safety routing

Before any model call:

1. Authenticate member.
2. Check entitlement.
3. Apply per-user daily limits.
4. Build deterministic fact-pack.
5. Evaluate red-flag thresholds.
6. If a red flag exists, return fixed urgent wording and do not call AI.
7. Apply GPU semaphore and deadline.
8. Retrieve only authorized records.

After generation:

1. Validate schema.
2. Cross-check numeric claims.
3. Apply deny lexicon.
4. Require citations for knowledge-base claims.
5. Append mandatory non-diagnostic disclaimer in code.
6. Persist interaction metadata.
7. Stream only approved output.

The model must not have:

- Database tools.
- Network tools.
- Billing tools.
- Notification tools.
- Write access.

# 9. API implementation conventions

All routes must:

- Use versioned `/api/v1`.
- Validate input and output with Zod.
- Return `application/problem+json` for errors.
- Enforce authentication at the route/plugin layer.
- Use service methods rather than repositories directly.
- Emit audit events for health, billing, consent, admin, and support operations.
- Support `Idempotency-Key` on mutating endpoints.
- Apply cursor pagination for collections.
- Avoid exposing internal database identifiers where a public resource identifier is more appropriate.

Example route structure:

```ts
app.post(
  "/api/v1/observations",
  {
    preHandler: [requireSession],
    schema: {
      body: ObservationCreateRequestSchema,
      response: {
        201: ObservationCreateResponseSchema,
      },
    },
  },
  async (request, reply) => {
    const result = await observationService.create({
      actor: request.user,
      input: request.body,
      idempotencyKey: request.headers["idempotency-key"],
      requestContext: request.context,
    });

    return reply.code(201).send(result);
  },
);
```
